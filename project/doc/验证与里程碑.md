### 3.2 关键结论：横带根因

> 现象：首图即有条带，位置每次上电不同，同一次会话内稳定；双读版更重。

定位过程（结论保留，过程省略）：

1. **改约束/打拍/加保护都无效** → 不是时序问题；M0 带着 -6.167ns 违例也能干净显示；
2. **自检（独占总线写 307200 字再读回）几乎全对** → SDRAM 存储本身没问题；
3. **冻结显示读后，连续多次加载全干净** → 根因是**显示读与帧写入并发**时控制器丢写；
4. 128 拍 burst 间隔保护无效 → 不是“两个 burst 挨太近”，而是加密控制器内部的读写模式切换行为。

### 3.3 解决方案：开机只写、运行只读

```
上电：扫描 4 张 BMP → 依次写入 SDRAM 槽 0..3（各 307200 字）
      期间 display_valid=0，帧缓存读被门控 → 绝不并发
运行：K1/轮播只改 disp_buf_idx（2bit 槽号）
      读引擎在下一帧边界换基地址 → 瞬间切换、无撕裂
```

槽位：`BUF0=0 / BUF1=307200 / BUF2=614400 / BUF3=921600`（共 1.2M 字 < 2M 字）。

### 3.7 M1 补丁：闲置槽噪点（2026-10-25）

**现象**：静止单张图若干分钟后，切到其它槽会出现稀疏、固定位置的单像素彩色噪点；正在显示的槽始终干净。

**定位**：

| 实验 | 结果 |
|:--|:--|
| 自检（独占总线写 307200 字再读回） | 几乎全对 → 存储与写路径正常 |
| `SELF_REFRESH_INTERVAL` /4 | 略微延缓，未消除 |
| 关闭控制器自刷新（`self_refresh_open=0`） | 未消除 |
| 按 128 字步长“点读”全片（每帧一遍 / 消隐期循环） | **完全无效** |
| 显示中的槽（每帧顺序读满） | 始终干净 |

**结论**：这颗嵌入式 SDRAM 的自动刷新对闲置行不足，且**只有“顺序整段读”会被当作有效访问**；点读无效。

**解决**：`sdr_refresh_sweep` 在每帧消隐期顺序读 4 个槽：

- M1 实际窗口：`fb_read_finish`（`v_cnt≈524`）至 `vs` 下降沿（`v_cnt=9`）共 `V_FP=10` 行（`320µs ≈ 40k` 字/帧），跨帧连续推进，4 槽 ≈31 帧读完一轮（≈0.52s）；
- M2 交接时序：因 `v_active` 在 `v_cnt==44 && h_cnt==15` 置起，但该行有效像素期间 `v_cnt` 已递增为 45，距首个有效像素（`h_cnt≈160`）仅 `5.8µs`（不够读 A+B 两行 `10.24µs`），M2 首行 `y=0` 必须在 `v_cnt=44` 提前一整行（~`37.8µs`）预取；而最后一行 `y=479` 在第 478 行（`v_cnt=523`）内即取完，故 M2 真实交接链为：**`最后一行取完 → 启动扫描 → 到 v_cnt=44（或满 150k 字）停止发 en → 排空 12~16 拍（保持 active=1） → 行读取接管`**（空闲约 44 行 `1.4ms`，稳跑 150k 字/帧）；
- 读数据不写 `rfifo`，对显示无影响；
- 实测静止 15 分钟以上切图无噪点。

**代价**：LUT +89（3,905 → 3,994），消隐期占用总线，帧率/加载时间不变。

### 3.8 M2 行缓冲/转场（2026-10-25）

**实现**：`line_sched` + `frame_line_read` + 2×`line_buffer` + `mixer` + `disp_ctrl`；每行取 A/B 各 640 字，溶解/水平滑动，自动轮播 4s。

**上板问题 1：首行预取早了两行**
- `v_active` 在 `v_cnt==44` 置起，但有效像素期间 `v_cnt=45`；原调度在 43 预取，显示第 0 行时正在写第 2 行，读写同一 bank；
- 修正为 `v_cnt=44` 预取 y=0，`45..523` 取 y=1..479；
- `tb_chain` 增加“有效显示期间写 bank 不得等于读 bank”断言：修复前 240 万次冲突，修复后 0。

**上板问题 2：行内像素错位/纵向梳齿**
- `frame_line_read` 最初在 `Sdr_busy` 时暂停 `App_rd_en`，一行 1280 字被拆成不连续小段，控制器返回节奏变化导致行内像素错位；
- 改为像 M1 `frame_fifo_read` 一样连续发完整 1280 个读命令，撕裂消失。

> **上板 bug 1 与修复（10-29）**：首版 bit 在真实卡上卡在彩条（第 3 张 1920×1080 预载时死锁）。
> 原因是行缓冲的“释放/装载”握手：① `buf_ready` 在行中途就置 1，半行被当成可用行；
> ② 用 `cur_y0` 游标释放旧行，缩小倍数 ≥2（y_step≥2）时游标会越过尚未装入的行，导致“释放早于装载”，
> 装载器随后把该行写回并把 `buf_free` 清零 → 缓冲区泄漏，输出永远等不到下一行 → 死锁。
> 修复：每个行缓冲带**行号标签**，只有“该行已被输出消费（行号 < 当前 y0）”才允许覆盖；整行写完才置有效。
> 该 bug 只影响缩小倍数 ≥2 的源图（1280×720/1920×1080 等），640×480 旁路与放大小图不受影响。

> **上板 bug 2 与修复（10-30）**：仍然卡彩条。用诊断 bit（数码管 + LED）定位到：
> `found=4`、`load_busy=1`、`finish_seen=0`、**旁路生效**，累计写入只差 **约 450~510 个像素**（<1 行）。
> 即板端 SD 字节流末端实际发出的像素比 307200 少了几百个，`frame_fifo_write` 数不满 `write_len=307200`
> 就永远不给 `write_finish` → 预载卡死。仿真里字节流是理想的，所以一直复现不了。
>
> 修复（`bmp_scale`）：**源读完（`src_eof`）但不足 307200 时用黑像素补满一帧**；
> 缩放路径同样在源行不足时用黑行补齐。这样帧一定写满、`write_finish` 一定到来；
> 代价只是最后一行的末尾几十~几百像素变黑，肉眼不可见。
> 验证：`tb_pad`（只送 306700 像素）输出仍为 307200、补齐部分全黑；`tb_sd_bmp` 真卡镜像 4 帧全过。
>
> **根因已在 §3.14 查清**（每行少 1 个像素），补黑保留为兜底。

**综合/布线**（首版）：Setup **+0.110ns** / Hold **+0.011ns**，0 失败；LUT 7,379（37.65%）、REG 5,268、BRAM9K 43（67.19%）、DSP 11（37.93%）。

### 3.14 M3 斜切根因与修复（2026-10-31，✅ 上板确认）

**现象**：经 `bmp_scale` 适配的源图（含 1:1 的 640×480）出现**约 1 px/行**的斜切，右缘可见重复段。
M2（无缩放）与片内图案自检都笔直。

**根因**：`bmp_read` 的字节相位寄存器在“行末字节到达之前”被清零：

```verilog
// 旧：row_byte_cnt 一走到 stride-1 就清零相位 —— 此刻行末字节还没来
if (row_byte_cnt == row_stride_r - 1)  bmp_byte_idx <= 0;
```

真实 SPI 是 **8 拍才来 1 个字节**，行末必然有空拍；空拍期间相位被清零，等真正的行末字节到来时
被当作“像素第 1 个字节” → **该行最后一个像素丢失** → 内容逐行左移 1 px。这就是板端“少 450~510 个像素”的来源。

**为什么仿真一直不复现**：仿真里的 SD 模型是**背靠背每拍一个字节**（没有空拍），bug 只在有空拍时发作。
这是本次排查最关键的教训：**测试台必须模拟外设的真实时序**。

**修复**

| 层次 | 改动 |
|:--|:--|
| 根因 | 相位改为“**行首字节强制归零**、其余只随有效字节推进”（`cur_phase`） |
| 结构加固 | `src_sop` 源行首标志 + 源 FIFO 加宽到 25bit + `bmp_scale` 行锁定/短行补黑 + `frame_fifo_write` 的 `App_wr_sop` 显式行对齐 |
| 清理 | 删除全部临时诊断（`DEBUG_SEG`、`dbg_*` 计数器、数码管调试显示），数码管恢复参数显示 |

**上板确认**：`main_project_m3_phasefix.bit` → 画面**笔直、边缘干净**；`m3-release`（= 本 RTL + 字幕透明）复测同样笔直。

**回归用例（锁住根因）**：`tb_bmp_read_pad0gap`（4×3 源图 + 字节间插 3 拍空拍，旧逻辑 9 个像素 / 1 个行首，新逻辑 12 / 3）、
`tb_scale_rowlock`（16×8 源图、第 2/5 行各少 1 像素，输出 32 像素且最后一行仍是源第 7 行）、
`tb_fb_sop`（每 7 行多 1 字，307200 字地址全对）。

### 3.18 M3.3 实时风格化滤镜（2026-10-31，创新点）

**动机**：赛题里「视频后处理」只要求亮度/对比度。加一个**实时风格化滤镜**能在现场直接用按键切换画面风格，
视觉冲击强、评委易感知，且**不需要额外素材、不额外占用 SDRAM 带宽**（只吃 1 块 BRAM）。

**实现**：新增 `video_fx`（`video/video_fx.v`），插在 `video_post` 内 `video_proc` **之前**。

| 项 | 做法 |
|:--|:--|
| 邻域获取 | **1 块** `2048×24` BRAM 做行延迟：`{I_y[0],I_x}` 写、`{~I_y[0],I_x}` 读，奇偶行分 bank，读写不冲突 |
| 可用窗口 | 2 行 × 3 列（`s_c/s_l/s_r` 当前行，`s_u/s_ul` 上一行） |
| 亮度提取 | `lum = R + 2G + B`（10bit，移位加法，0 乘法器） |
| 边缘强度 | `grad = abs(Δlum_x) + abs(Δlum_y)`，卡通模式 `grad > 96` 判边（8bit 饱和） |
| 8 种模式 | `0` 直通 / `1` 锐化 / `2` 线稿 / `3` 浮雕 / `4` 卡通（4 级量化 + 描边） / `5` 灰度 / `6` 反色 / `7` 暖调 |
| 延迟 | **固定 3 拍**，`de/x/y` 同步延迟；`video_post` 总延迟 3 → **6 拍** |
| 按键 | **K14**（`key_press[13]`）循环 `F0..F7`；K12 一键复位同时清 `fx_mode` |
| OSD | 面板扩为 **3 行 20 列**（`160×52`），第 3 行实时显示 `F0..F7` |

**为什么放在 `video_proc` 之前**：先风格化再调亮度，语义更自然（也让「灰度模式下亮度键依然有效」这类演示成立）。
**为什么不吃 SDRAM 带宽**：锐化/卡通只需**同一帧内**相邻行，行延迟在片内 BRAM 完成，不做跨源 A/B 的 3×3 取窗。
